# Internal Task & Management Dashboard

## Project Overview

A full-stack internal tool for a team to create, assign, track, and comment on tasks from a central dashboard. Built to demonstrate a properly structured, reusable full-stack setup: a typed API contract shared between backend and frontend, a modular Express backend, and a component/hook-driven React frontend.

## Tech Stack

| Layer | Choice |
|---|---|
| Frontend | React + Vite + TypeScript + Tailwind CSS + Material UI |
| Backend | Node.js + Express + TypeScript |
| Database | SQLite (via Prisma ORM) — zero-install, a local file. Swappable to PostgreSQL (see [Assumptions](#assumptions--decisions)) |
| Shared | `packages/shared-types` — one TypeScript package with the DTOs/enums both sides import, so the API contract can't silently drift |

## Prerequisites

- Node.js 20+ (no database server, no Docker, no cloud account needed)

## Setup

```bash
# 1. Install all workspace dependencies (root, backend, frontend, shared-types)
npm install

# 2. Build the shared types package (backend imports its compiled output)
npm run build -w packages/shared-types

# 3. Configure environment variables
cp .env.example backend/.env
cp .env.example frontend/.env

# 4. Create the SQLite database and tables (creates backend/prisma/dev.db)
npm run db:migrate

# 5. Seed sample data (4 users, 14 tasks, a handful of comments)
npm run db:seed
```

## How to Run

**Both at once, from the repo root:**
```bash
npm run dev
```

**Or separately, in two terminals:**

Backend (http://localhost:4000):
```bash
cd backend
npm run dev
```

Frontend (http://localhost:5173):
```bash
cd frontend
npm run dev
```

Open http://localhost:5173. `GET http://localhost:4000/health` is a quick liveness check for the API on its own.

`npm run db:studio` (from the root, or inside `backend/`) opens Prisma Studio, a GUI for browsing/editing the SQLite data directly.

## Database

Schema lives in `backend/prisma/schema.prisma`; migrations are generated by Prisma into `backend/prisma/migrations/` (created the first time you run `npm run db:migrate`). Seed data is in `backend/prisma/seed.ts`.

```
User (id, name, email unique, role, createdAt)
  └─< Task (id, title, description, status, priority, assignedTo → User, dueDate, createdAt, updatedAt)
        └─< Comment (id, taskId, userId → User, comment, createdAt)
```

- `status`: `PENDING | IN_PROGRESS | COMPLETED | BLOCKED`
- `priority`: `LOW | MEDIUM | HIGH | URGENT`
- Stored as validated strings rather than a native DB enum (SQLite has no enum type) — enforced by zod at the API boundary using the same values declared once in `packages/shared-types`.
- "Overdue" is **derived**, not stored: `status != COMPLETED AND dueDate < now`.
- Deleting a task cascades its comments.

## API Documentation

Base path `/api`. Every success response is `{ data, meta? }`; every error is `{ error: { message, details? } }`.

### Tasks
| Method | Path | Description |
|---|---|---|
| GET | `/api/tasks` | List tasks. Query params: `status`, `priority`, `assignedTo`, `search` (matches title/description), `sortBy` (`title\|status\|priority\|dueDate\|createdAt\|updatedAt`), `sortDir` (`asc\|desc`), `page`, `limit`. Filtering/sorting/pagination all happen in the DB query, not in the frontend. Returns `{ data: Task[], meta: { total, page, limit, totalPages } }`. |
| GET | `/api/tasks/:id` | Fetch one task, with assignee and comments (+ comment authors). 404 if missing. |
| POST | `/api/tasks` | Create a task. Body: `{ title, description?, status?, priority?, assignedTo?, dueDate? }`. `title` is required; everything else has a default or is nullable. 400 on validation failure. |
| PUT | `/api/tasks/:id` | Update a task (partial body, same shape as create). 404 if missing, 400 on validation failure. |
| DELETE | `/api/tasks/:id` | Delete a task (cascades its comments). 204 on success, 404 if missing. |
| GET | `/api/tasks/:id/comments` | List comments on a task. |
| POST | `/api/tasks/:id/comments` | Add a comment. Body: `{ userId, comment }`. 404 if the task or user doesn't exist. |

### Users
| Method | Path | Description |
|---|---|---|
| GET | `/api/users` | List all users. |
| POST | `/api/users` | Create a user. Body: `{ name, email, role? }`. 409 on duplicate email. |

### Dashboard
| Method | Path | Description |
|---|---|---|
| GET | `/api/dashboard?userId=` | Aggregate counts: `total, pending, inProgress, completed, blocked, overdue, assignedToMe`. `assignedToMe` is 0 unless `userId` is passed. Computed via grouped SQL counts, not by loading every row. |

### External API Integration
| Method | Path | Description |
|---|---|---|
| GET | `/api/external/users` | Fetches sample users from [JSONPlaceholder](https://jsonplaceholder.typicode.com/users) (a free public API, no key required), demonstrating third-party integration: a 5s request timeout via `AbortController`, upstream failures mapped to `502`, and a 60s in-memory response cache so the dashboard doesn't hit the upstream API on every load. Displayed in the "Team Directory" card on the Dashboard. |

### Errors
Zod validation failures return `400` with field-level `details`. Missing resources return `404`. Duplicate-email conflicts return `409`. Everything else funnels through one Express error-handling middleware to a `500`.

## Assumptions & Decisions

- **SQLite over PostgreSQL.** The assignment marks both as acceptable; SQLite was chosen so the project runs with zero external services (no Docker, no DB server, no cloud signup) — `npm run db:migrate` just creates a local file. To switch to Postgres: change `schema.prisma`'s `datasource.provider` to `"postgresql"`, point `DATABASE_URL` at a real connection string (e.g. via Docker or a hosted instance), and re-run migrations.
- **No login/authentication.** There's a lightweight "acting as" user switcher (top-right dropdown) instead — it drives the "assigned to me" dashboard stat and task filter, persisted to `localStorage`. It's a UX convenience for a single-team internal tool, not an auth boundary. Real auth would mean replacing that context with a login flow and adding JWT middleware on the backend.
- **Prisma over a raw query builder.** Chosen for typed queries, built-in migrations, and to keep the schema (and its relations) declarative and easy to read in one file.
- **No automated test suite** was in scope for this pass; service functions are plain data-in/data-out (no framework coupling), so they're straightforward to unit test, and each endpoint is a natural integration-test seam if added later.

## Reusability

The parts of this codebase meant to outlive this specific app:


- **`packages/shared-types`** — the DTO/enum contract both sides import, instead of duplicating types or trusting them to stay in sync by convention.
- **Backend module pattern** (`modules/<resource>/{routes,controller,service,schema}.ts`) — a new resource is a copy of one folder with the Prisma model/zod schema swapped in. `middleware/` and `utils/` are already resource-agnostic.
- **`components/common/DataTable`** — a generic, column-config-driven table with server-driven sort/pagination and zero Task-specific logic; any future list page reuses it with different columns.
- **`components/common/{FilterBar, ConfirmDialog, EmptyState, StatusBadge, PriorityBadge}`** — generic UI primitives.
- **`api/` + `hooks/` pattern** — one thin axios module and one hook per resource, consistent enough that a new resource's client/hook pair is a copy-paste-and-rename job.
